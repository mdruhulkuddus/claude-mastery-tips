Phase 1: প্রজেক্ট সেটআপ

FOUNDATION — এটা ছাড়া বাকি সব অকার্যকর
📄 CLAUDE.md তৈরি করুন — Claude-এর মস্তিষ্ক
এই ফাইলটি Claude প্রতিটি মেসেজে পড়ে। এটাই Claude-কে আপনার প্রজেক্ট সম্পর্কে "ট্রেইন" করার মূল উপায়। প্রজেক্টের root folder-এ তৈরি করুন।
CLAUDE.md # Project: Clean Code Bangla

## Overview
বাংলায় Clean Code শেখার interactive ওয়েবসাইট।
Static site — HTML, CSS, JS। কোনো framework নেই।

## Structure
index.html — মূল landing page
style.css — সমস্ত styling
script.js — interactivity ও navigation
chapters/ — প্রতিটি অধ্যায়ের HTML ফাইল

## Coding Rules
- Semantic HTML5 tags ব্যবহার করো
- BEM naming convention (CSS)
- Mobile-first responsive design
- সব content বাংলায়
- Comments ইংরেজিতে

## Current State
- ৫টি অধ্যায় সম্পন্ন
- Dark mode আছে
- Mobile responsive
⚠️ গুরুত্বপূর্ণ

Phase 2: প্রজেক্ট Training — Claude-কে বোঝানো

CONTEXT BUILDING — Claude আসলে "ট্রেইন" হয় না, বোঝানো হয়
💡 বোঝা দরকার
Claude-কে সত্যিকারের "training" করা যায় না যেমন ML model-কে করা হয়। Claude প্রতিটি conversation-এ CLAUDE.md + আপনার prompt + open files পড়ে context বোঝে। তাই "training" মানে হলো Claude-কে সঠিক context দেওয়া।
🗺️ Step-by-Step: Claude-কে আপনার প্রজেক্ট বোঝানো
1

প্রথম conversation: প্রজেক্ট পরিচয়

VS Code-এ Claude Code open করে প্রথমেই প্রজেক্টের overview দিন। Claude CLAUDE.md পড়বে, কিন্তু আপনি চাইলে আরো context দিতে পারেন।

// প্রথম prompt — প্রজেক্ট বোঝানো

"আমার প্রজেক্টটি দেখো। এটি বাংলায় Clean Code
শেখার একটি ওয়েবসাইট। index.html হলো main page,
chapters/ ফোল্ডারে অধ্যায়গুলো আছে।
style.css-এ BEM convention ব্যবহার করা হয়েছে।
প্রজেক্টের structure ও coding pattern বুঝে নাও।"
2

Pattern বোঝানো: একটি example দেখান

Claude-কে বলুন বিদ্যমান কোড দেখে pattern বুঝতে, যাতে নতুন কোডও একই ধরনের হয়।

"chapters/chapter-01.html ফাইলটি দেখো।
এই pattern অনুযায়ী ভবিষ্যতের সব chapter
তৈরি হবে। HTML structure, class naming,
এবং content format বুঝে নাও।"

Rules ও Constraints বলুন

Phase 3: নতুন Feature পরিকল্পনা

PLAN BEFORE CODE — এতে token ও সময় দুটোই বাঁচে
🎯 Feature Request-এর আদর্শ Structure
কোড লেখার আগে Claude-কে plan করতে বলুন। এতে ভুল কম হয়, revision কম লাগে, token বাঁচে।
// আদর্শ Feature Request Template

"আমি একটি নতুন feature চাই: [feature নাম]

🎯 কী করবে:
[feature-এর বিস্তারিত বর্ণনা]

📁 কোন ফাইলে পরিবর্তন হবে:
[নির্দিষ্ট ফাইলের নাম]

⚙️ Technical Details:
[ব্যবহৃত technology, API, library]

🚫 Constraints:
[কী করা যাবে না / সীমাবদ্ধতা]

প্রথমে plan দাও, কোড পরে লিখবে।"
💡 Real Example: আপনার প্রজেক্টে Search Feature যোগ করা
ধরুন আপনি CLEAN-CODE-BANGLA প্রজেক্টে search feature যোগ করতে চান:
✗ খারাপ Prompt
  • "search feature যোগ করো"
  • কোন ফাইলে? কিসে search?
  • Claude guess করবে → ভুল হবে
  • বারবার ঠিক করাতে token যাবে
✓ ভালো Prompt
  • কী search করবে: chapters-এর content
  • কোথায় দেখাবে: index.html-এ top-এ
  • কোন ফাইলে কাজ: script.js ও style.css
  • Constraint: No library, vanilla JS only
// ভালো prompt example

"আমি chapters-এর content-এ search করার
feature চাই।

কী করবে: ইউজার text লিখলে chapters/ folder-এর
সব HTML file-এ content search করে matching
results দেখাবে।

কোথায়: index.html-এ navigation-এর নিচে একটি
search bar থাকবে।

ফাইল: index.html (search bar HTML),
style.css (styling), script.js (search logic)

Constraints: Vanilla JS only, কোনো library নয়।
বিদ্যমান BEM naming convention follow করবে।

প্রথমে plan দাও, তারপর কোড লিখবে।"

💡 কেন এটা গুরুত্বপূর্ণ
Plan ছাড়া সরাসরি কোড লেখালে Claude হয়তো ভুল approach নেবে। তখন "এটা ঠিক করো", "না, এভাবে করো" — এই revision গুলোতে ৩-৫ গুণ বেশি token খরচ হয়। আগে plan approve করলে একবারেই সঠিক কোড আসার সম্ভাবনা অনেক বেশি।

Phase 4: Feature Development — কোড লেখানো

BUILD SMART — Token-efficient কোডিং কৌশল
📐 কৌশল ১: ছোট ছোট ভাগে কাজ করুন
একটি বড় feature একবারে না করে ছোট ছোট অংশে ভাগ করুন। প্রতিটি অংশ শেষ করে commit করুন, তারপর পরের অংশে যান।
// ❌ একটি giant prompt — ভুলের সম্ভাবনা বেশি
"পুরো search feature বানাও — HTML, CSS, JS,
results page, filtering, sorting সব একসাথে"

// ✅ ভাগ করে করা — প্রতিটি ধাপ verified
Prompt 1: "search bar-এর HTML ও CSS বানাও"
→ verify → commit

Prompt 2: "search logic (JS) implement করো"
→ verify → commit

Prompt 3: "results highlighting যোগ করো"
→ verify → commit
💡 কেন ভাগ করবেন
প্রতিটি ধাপে ভুল ধরা সহজ। যদি ৩য় ধাপে সমস্যা হয়, শুধু সেটাই ঠিক করতে হবে — পুরো feature আবার লেখানো লাগবে না। এতে অনেক token বাঁচে।
🎯 কৌশল ২: নির্দিষ্ট ফাইল ও লাইন বলুন
Claude-কে যত নির্দিষ্ট করে বলবেন, তত কম ফাইল scan করবে = কম token।
Token বেশি যায়
  • "navigation fix করো"
  • "CSS ঠিক করো"
  • "এই bug fix করো"
Token কম যায়
  • "script.js-এর toggleNav() function fix করো"
  • "style.css-এ .nav__menu class-এ mobile breakpoint যোগ করো"
  • "index.html-এর line 45-এ link ভুল, chapters/ch3.html হবে"
🔗 কৌশল ৩: Reference দিন — বিদ্যমান pattern দেখান
নতুন কিছু তৈরি করাতে চাইলে বিদ্যমান pattern reference হিসেবে দিন। Claude সেই pattern follow করবে।
"chapters/chapter-01.html-এর মতো structure-এ
chapter-06.html তৈরি করো।

বিষয়: SOLID Principles
chapter-01.html-এর HTML structure, CSS classes,
এবং section layout হুবহু follow করো।
শুধু content আলাদা হবে।"
💡 কেন কাজ করে
Claude-কে reference দিলে সে নিজে pattern বোঝে এবং consistent কোড লেখে। আলাদা করে styling rules বলতে হয় না — token বাঁচে, consistency বাড়ে।
⚡ কৌশল ৪: একটি Prompt-এ একাধিক সম্পর্কিত কাজ
যদি কয়েকটি কাজ একই ফাইলে বা একে অপরের সাথে সম্পর্কিত হয়, একটি prompt-এ দিন।
"style.css-এ নিচের ৩টি কাজ করো:

1. .chapter__title-এ font-size mobile-এ 24px করো
2. .chapter__content-এ line-height 1.8 করো
3. .chapter__code-block-এ dark theme color
#1a1b26 background দাও"
✅

Claude code লেখে → আপনি verify করেন
Commit করুন → CLAUDE.md update করুন
পরের feature → নতুন session (যদি context বড় হয়)
